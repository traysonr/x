PROJECT LOG / STARTED 2026.09

433Link: a PIC-to-Pi radio link

A small custom packet link between a Raspberry Pi 3 and a dsPIC33CK64MC105, using inexpensive 433 MHz ASK/OOK modules. The first milestone is deliberately one way: get a known PIC packet into the Pi, validate it, then work toward ACKs and retries.

  • Embedded systems
  • Raspberry Pi
  • dsPIC33
  • Python
  • 433 MHz RF

I wanted a radio project where I could follow the whole path: bytes in firmware, a signal over the air, and a decoded packet on a Raspberry Pi. The FS1000A modules are cheap and a little rough around the edges, which makes them a good excuse to learn the framing and timing instead of treating the radio as a black box.

The first target is a known DATA packet from the PIC to the Pi. Once that works reliably, the plan is to add acknowledgements and retries. So far the useful progress is the shared protocol contract and a tested, hardware-independent Pi implementation. The repository does not yet show a verified over-the-air packet; the GPIO receiver and PIC firmware still need to meet at the bench.

The 433Link repository has the protocol contract, Pi reference code, and PIC handoff notes.

27 Sep 2026 12:39

First question: how much of the radio should I build myself?

The idea was to get a PIC and a Raspberry Pi talking over a pair of inexpensive FS1000A 433 MHz modules. I wanted to learn the whole path, but didn’t want to invent a protocol just for the sake of it. The useful split was to borrow the familiar pieces—preamble, sync, balanced coding, length, checksum—and define a small shared contract both ends could implement.

The first proof is intentionally one way: make the PIC send a known DATA packet and have the Pi receive and validate it. If that behaves, add acknowledgements and retries. Keeping the first milestone narrow gives us a clean place to debug before adding a round trip.

27 Sep 2026 15:28

Write the packet contract before either side drifts

I set up one repository for both processors: a shared protocol document at the root, a Raspberry Pi implementation, and a PIC handoff area. That gives the two sides one place to agree on bytes and timing while leaving timer and GPIO details with the firmware they belong to.

Protocol v1 uses ASK/OOK at a nominal 2,000 bits per second. Each logical bit becomes a Manchester pair (0 → 01, 1 → 10), preceded by eight 0x55 bytes and sync D3 91. The packet carries version, type, source, destination, sequence, payload length, up to 32 payload bytes, then CRC-16-CCITT. That is enough structure to reject noise and malformed frames without making the first firmware pass huge.

The known DATA vector is 01 01 01 02 00 03 11 22 33 98 0E: PIC address 01, Pi address 02, payload 11 22 33, and CRC bytes 98 0E. The CRC and byte order are spelled out in the protocol file so neither implementation has to guess.

30 Sep 2026 17:32

The wiring question was part of the protocol work

When the modules came out on the bench, the receiver’s 5V marking raised the important question: what voltage is actually coming back out of DATA? The Pi’s GPIO is 3.3 V. Feeding the module from 5 V does not make a 5 V DATA output safe for a Pi pin.

The sensible next step is to measure the receiver output and use a level shifter or divider if it exceeds the Pi’s input limit. The conversation stopped before that was verified, and I don’t see a captured packet or concrete GPIO receiver in this repo. So the honest status is: protocol and offline software are in place; the first over-the-air receive is still ahead.

30 Sep 2026 17:48

Make the packet work in software before blaming the air

The Pi side now has a small, testable path for building and checking packets: a packet model, CRC, Manchester codec, and a frame parser that searches for preamble/sync before validating length and checksum. The conversation’s Pi session reported 63 pytest checks passing. That’s encouraging for the software protocol path; it says nothing yet about receiver timing over the radio.

One useful design boundary is still visible in the code: GPIO timing is an interface, not a finished pigpio implementation. The current command-line tool decodes logical packet bytes offline. The PIC folder in this repository is still a handoff/readme, so I’m not counting firmware behavior as demonstrated here.
